# 37 — Release Management

## Document Scope

This document defines the official Release Management process for Version 1 of the Unified Education Platform. It describes how versions are planned, prepared, tested, approved, released, and maintained throughout the software lifecycle.

It is a process and governance document only. It does not define source code, deployment scripts, CI/CD pipeline definitions, infrastructure-as-code, database tables, SQL, API implementation, or UI implementation.

`AI_DOCS/00_Project_Context.md` is the official Single Source of Truth and prevails if any conflict is found. The technology baseline is built on **Laravel 12** backend with **PHP 8.3**, **React 19** frontend with **TypeScript**, **Vite**, **Tailwind CSS**, **MySQL 8**, **Laravel Sanctum**, **Laravel Gates & Policies with Custom RBAC**, **File Cache**, **Database Queue**, **Database session driver**, **Laravel Public Storage**, **Laravel Scheduler with Cron Jobs**, **SMTP** baseline, **Apache or LiteSpeed**, on **cPanel Shared Hosting** primary target with **VPS / Cloud** as future target, per `03_System_Architecture.md` §4.1 and `29_Project_Decisions.md` D-001, D-044.

Release versioning, branch naming, tagging, merge strategy, and rollback mechanics are owned at the Git level by `36_Git_Workflow.md`; this document owns the planning, approval, checklist, documentation, communication, risk, and lifecycle governance of a release.

**Authoritative sources:** `00_Project_Context.md`, `03_System_Architecture.md`, `04_Project_Structure.md`, `24_Testing_Strategy.md`, `26_Deployment_Plan.md`, `27_Development_Roadmap.md`, `28_Coding_Standards.md`, `29_Project_Decisions.md`, `30_Project_Glossary.md`, `31_Master_Index.md`, `35_Environment_Configuration.md`, `36_Git_Workflow.md`.

# 1. Document Purpose

The purpose of this document is to provide one authoritative reference for every release management question for the Unified Education Platform:

- How versions are numbered using Semantic Versioning (SemVer) and what each segment means in the context of a frozen Version 1 scope.
- Which release types exist, their intent, their origin branch, and their target environment.
- How a Development release moves to Testing release, to Release Candidate (RC), to Production release, and how Hotfix and Patch releases interrupt that flow.
- How release approval is governed, who must approve, and which quality gates must pass before any cPanel Shared Hosting deployment.
- Which pre-release and post-release checks must be satisfied, aligned with deployment checklists and environment checklists.
- How rollback is decided, executed, and communicated when Critical defects, isolation breaches, or historical data issues are discovered.
- How release documentation and change logs are authored to remain consistent with previous documents and canonical terminology.
- How release communication reaches Super Admin, Teacher, Teacher Staff, Student, and Parent without introducing notification features out of scope.
- How risks are managed, how emergency releases are handled, and how the process evolves toward future continuous delivery on VPS and Cloud.

Out of scope and explicitly prohibited in this document per task requirements: CI/CD pipeline definitions, pipeline file contents, deployment shell command sequences, Cron command contents, source code, API definitions, database tables, UI markup. This document describes *what must be proven* and *who must approve*, not executable commands.

# 2. Release Management Philosophy

Release management inherits the project's core principles from `00_Project_Context.md` §17 and `27_Development_Roadmap.md` §2 and the Git philosophy from `36_Git_Workflow.md` §2:

1. **Documentation before code applies to releases.** No version is cut without a confirmed requirement traceable to BR-xxx, D-xxx, and `02_Software_Requirements.md`. History that cannot be traced is a defect, mirroring Audit Log mandatory traceability.

2. **One codebase, one releasable main.** Main is the single source of deployable truth per `36_Git_Workflow.md` §5. Production releases originate only from main or from release branches that merge to main. Main is always in a state where all tests could pass.

3. **Tenant isolation is release-blocking.** Teacher Workspace isolation BR-003 is the highest-priority invariant. Any release candidate that shows cross-Teacher data visibility, whether through API, search, report, file access, cache, or error message, fails acceptance and must not proceed to Production.

4. **Archive philosophy extends to releases.** Releases are never deleted. Tags are immutable per `36_Git_Workflow.md` §15. Failed releases remain in history as traceable records, analogous to BR-005 Archive replaces deletion and BR-014 historical data never deleted. Rollback creates a new version, never rewrites published history.

5. **Small, reversible increments.** Each release represents a coherent increment from the ten-phase roadmap `27_Development_Roadmap.md` §3. Feature branches per §4 of Git Workflow keep increments small and traceable. Large releases spanning many unrelated modules are discouraged because they obscure bisect, review, and rollback.

6. **Solo efficiency with future team rigor.** For solo development, approval may be self-review with documented delay, but checklist discipline from `24_Testing_Strategy.md` §20, `26_Deployment_Plan.md` §26, and `35_Environment_Configuration.md` §22 must still be satisfied. Future team adds reviewer count, not process rewrite.

7. **cPanel compatible by design.** Version 1 releases must operate within cPanel Shared Hosting resource limits: File Cache, Database Queue, Database session driver, Laravel Public Storage, Scheduler via cPanel Cron Jobs, no Docker, Redis, Kubernetes, S3, WebSockets, Microservices. Future migration to VPS/Cloud `26_Deployment_Plan.md` §24-§25 must not change past release guarantees.

8. **No out-of-scope leakage via releases.** Releases must never introduce native mobile application BR-017, payment gateways BR-019, notifications D-012, marketplace browsing, course discovery, video homework BR-021, multiple Teaching Subjects per Teacher BR-016, multiple Parents per Student BR-020 as V1 capability. PENDING items Q-005 non-payment enforcement, Q-010 Lesson video hosting/protection, Q-011 Teacher Staff permission granularity, Q-012 Super Admin content visibility, Q-013 flat vs tier pricing, Q-015 timezone/currency must remain PENDING and never hardened by a release.

9. **Canonical terminology in release artifacts.** Release names, tags, change logs, approval records, communication use canonical terms: Platform, Teacher Workspace (tenant only in architecture discussion), Educational Grade (never Class), Teaching Subject (never Course), Group, Student, Parent, Teacher Staff (never sub-teacher), Super Admin, Subscription for Flow A only, payment status for Flow B, Price Per Student, Pricing Type Monthly/Per Lesson, Enrollment, Archive (never Delete as product behavior), Audit Log, Dynamic QR Code, ID Card, Question Bank, Bubble Sheet, Student Switcher, Lesson (never Course), Billable Student enrollment duration more than 15 calendar days BR-008, Billing Cycle calendar month D-006, Homework Text/Image/PDF only.

# 3. Version Numbering Strategy

Version numbering follows **Semantic Versioning (SemVer)** MAJOR.MINOR.PATCH as established in `27_Development_Roadmap.md` §18.2 and `36_Git_Workflow.md` §15.

**Format:**

- Tag format with leading `v` prefix: `vMAJOR.MINOR.PATCH`, for example `v1.0.0` initial Version 1 production release, `v1.0.1` hotfix, `v1.1.0` enhanced operations.
- Annotated tag with tagger identity, date, message referencing roadmap milestone and decision log.

**Semantics for this Platform:**

- **MAJOR:** Significant product scope change, potentially including new roles, new modules, or confirmed infrastructure changes. For Version 1, MAJOR is 1 and remains 1 until Product Owner approves scope expansion. MAJOR increment requires new decision entries in `29_Project_Decisions.md` and unfreezing consideration of `00_Project_Context.md` which is frozen at 2.0 FINAL. MS: increment only with Product Owner authority.

- **MINOR:** Feature additions or improvements within confirmed Version 1 architecture and stack, without changing frozen business rules. Examples after V1: enhanced Teacher Staff permissions after Q-011 resolved, Super Admin visibility refinement after Q-012 resolved, non-payment enforcement after Q-005 resolved, pricing model refinement after Q-013 resolved, enhanced reporting or search improvements after approval. Minor increments originate from release branches merging to main.

- **PATCH:** Bug fixes, security patches, minor corrections that do not change confirmed product scope. Examples: isolation fix, duplicate Student prevention fix, Archive enforcement fix, Audit Log gap fix, validation fix, error message safety fix. Patch increments originate from hotfix branches per `36_Git_Workflow.md` §7 or bugfix branches merging to develop then release.

**Pre-release identifiers for validation:**

- For staging validation, pre-release identifiers may be used conceptually: `v1.0.0-rc.1`, `v1.0.0-rc.2` marking release candidates tested on staging per `36_Git_Workflow.md` §15. These tags originate from release branches, not main, and are distinct from production tags. Production tags never carry rc suffix.

**Immutability:**

- Once published, version tag never moved or deleted per `36_Git_Workflow.md` §15. If defect discovered after tag, new patch tag via hotfix branch. Tag history append-only, mirroring Audit Log immutability BR-006.

**API versioning alignment:**

- All Version 1 REST endpoints use `/api/v1` prefix per `10_API_Design.md` §5. Product version MAJOR increment does not automatically imply API MAJOR increment; API versioning governed by `10_API_Design.md` and remains `/api/v1` throughout Version 1. Breaking API changes require future API version, recorded separately.

**Mapping to deployment milestones:**

- DE1 provisioning no tag. DE2-DE8 staging updates are integration of develop, not production tags. DE9 production preparation corresponds to release candidate tag from release branch. DE10 production deployment corresponds to production tag on main.

# 5. Development Release Process

Development release corresponds to integration of feature work into develop for local verification per `04_Project_Structure.md` root layout and `27_Development_Roadmap.md` phases.

**Trigger:** Feature branch completes single objective per `36_Git_Workflow.md` §6, e.g., Group Pricing Type Monthly/Per Lesson BR-009, Enrollment time-bounded per BR-002/BR-007, Student Switcher BR-020.

**Governance:**

- Branch originates from current develop tip, naming per §9 of Git Workflow: `feature/educational-grades-crud`, `feature/attendance-dynamic-qr-daily`, `feature/students-dual-registration-br022`.
- Commits follow convention `28_Coding_Standards.md` §14: type(scope): description, e.g., `feat(attendance): add Dynamic QR Code daily generation`, traceability footer referencing BR-xxx, D-xxx.
- Pull request to develop includes purpose, scope boundaries Teacher Workspace, roles affected, business rules list, decisions, testing evidence per `36_Git_Workflow.md` §11 checklist.

**Quality gates before develop merge:**

- Teacher Workspace isolation verification for all workspace-owned queries: Educational Grades, Groups, Students, Enrollments, Attendance Sessions, Attendance records, Homework, Homework Submissions, Lessons, Lesson Videos, Question Bank, Questions, Exams, Exam Attempts, Exam Answers, Reports, Teacher Staff, Settings, payment-status, file references.
- No permanent deletion; Archive used BR-005; archived excluded from active searches/dropdowns, included in reports with indication per Project Context §11.
- Historical preservation: Student transfers preserve attendance/homework/exams/grades BR-007, Billing Cycle history BR-014.
- One Group per Student per Teacher BR-002 enforced, duplicate Student prevention BR-001/BR-022, one Parent per Student BR-020, Parent read-only BR-004, Teaching Subject immutability BR-016, Homework Text/Image/PDF only BR-021, Question Bank private four types BR-011.
- Flow A/B separation: Subscription (Flow A) vs payment status (Flow B), labels separate `subscriptions` vs `payments` per Project Structure §3.
- Canonical terminology verification: Educational Grade not Class, Lesson not Course, Archive not Delete, Teacher Workspace not tenant in product contexts.

**Environment tie-in:**

- Uses Development environment `35_Environment_Configuration.md` §4: PHP 8.3, MySQL 8, Composer, Node.js/npm for Vite build of React 19, local cPanel-compatible stack, local `.env` from `.env.example`, unique local `APP_KEY`, drivers fixed database/file/database/public/smtp per D-040-D-043.

**Output:** Develop tip advances, no production tag. Development release remains internal; staging not yet updated until deployment milestone DE.

**Solo optimization:** Solo developer may self-review with documented delay per `36_Git_Workflow.md` §12, but must still run relevant test subsets locally: Unit for Billable Student >15 days, Feature for isolation, Database for constraints.

# 6. Testing Release Process

Testing release corresponds to automated validation of develop tip per `24_Testing_Strategy.md` and environment parity per `35_Environment_Configuration.md` §5.

**Trigger:** Develop receives new merge from feature, bugfix, docs, chore, refactor branch, or AI arena branch merge.

**Governance:**

- Testing environment definition per `35_Environment_Configuration.md` §5: dedicated MySQL 8 test database separate from Development/Staging/Production, same stack File Cache Database Queue Database sessions, no Docker/Redis, Database Queue used also in Testing, test data clearly identifiable and separable, no production data copy without sanitization.
- Testing scope per `24_Testing_Strategy.md` §3.1 in-scope: authentication, authorization five roles, isolation, Educational Grades, Groups, Students, Attendance three methods, Homework, Exams four types, Lessons private, Reports workspace-scoped, Payments status only Flow B, Subscriptions Billable Student calculation BR-008 Billing Cycle calendar month, Teacher Staff, Settings, Files, Archive, Audit Log ten mandatory events, Background Jobs, Search & Filtering scope before filtering, Security.
- Out-of-scope per §3.2: native mobile BR-017, payment gateways BR-019, notifications D-012, marketplace, video homework BR-021, multiple Teaching Subjects BR-016, multiple Parents BR-020, Docker/Redis/K8s/S3/WebSockets, PENDING Q-005/Q-011/Q-012/Q-015.

**Quality gates:**

- Business rule regression: every BR-xxx has automated test; changes must not break.
- Authorization regression: complete matrix for all five roles per §10 of Testing Strategy.
- Tenant isolation regression: cross-Teacher isolation tests pass.
- Archive regression: Archive/Restore tests for all archivable entities.
- Audit Log regression: all ten mandatory events Create/Update/Archive/Restore/Login success/failure/Permission Change/Attendance Change/Exam Modification/Homework Modification/Subscription Change.
- Flow separation regression: Flow A/B tests.
- cPanel compatibility: MySQL 8, File Cache, Database Queue, Database sessions.

**Outcome:** Testing release provides evidence for pull request description: which layers executed Unit/Feature/Integration/API/Authentication/Authorization/Database/UI/Performance/Security/Regression.

**No tag:** Testing releases do not create production tags; they validate develop readiness for release branch creation at milestone boundary per roadmap testing milestones T1-T10.

# 7. Release Candidate (RC) Process

RC process stabilizes a version on release branch per `36_Git_Workflow.md` §8 and roadmap deployment milestones DE2-DE9.

**Creation trigger:**

- Develop reaches feature completeness for milestone: M3 Teacher Workspace complete, M5 Attendance complete, M7 Exam Engine complete, M9 Subscription/Billing complete, M10 Optimization complete. Product Owner confirms scope lock per `27_Development_Roadmap.md` §18.3.

**Branch and tag governance:**

- Release branch originates from develop tip, naming `release/1.0` for Version 1 initial, `release/1.1` for future enhanced operations per roadmap §20.1.
- Develop reopens immediately for next phase work after RC branch creation, mirroring roadmap overlapping validation.
- Pre-release tag `v1.0.0-rc.1` created from release branch for staging deployment, not from main. Each hardening iteration increments rc number.

**Hardening allowed during RC lifecycle (only):**

- Bug fixes for Critical/High/Medium per `24_Testing_Strategy.md` §17.1: isolation breach, duplicate Student, Archive bypass, Billable Student edge, Homework format, Student Switcher linked-only.
- Security hardening per `23_Security_Standards.md` §21 checklist: input validation, SQL injection prevention via parameterized Eloquent, XSS via React auto-escaping, CSRF tokens Sanctum SPA XSRF-TOKEN/X-XSRF-TOKEN, rate limiting via File Cache, session flags HttpOnly/Secure/SameSite.
- Performance tuning preserving isolation per `25_Performance_Scalability.md`: query scoping, eager loading, pagination, cache scoping.
- Documentation corrections: Master Index §15 purpose/dependencies/owner, glossary term addition if term already used.

**Prohibited during RC:**

- New features, scope expansion, marketplace browsing endpoint, payment gateway integration, notification send logic, video homework acceptance, multiple Teaching Subjects per account, multiple Parents per Student, Docker/Redis/K8s/S3/WebSockets/Microservices as mandatory. Violation blocks release.

**Staging validation per `35_Environment_Configuration.md` §6.2:**

- Own database instance MySQL 8 utf8mb4_unicode_ci, own `.env`, own storage paths teacher-workspaces/lessons/homework/files and student-homework, own `APP_KEY`, database not shared with Production `26_Deployment_Plan.md` §23.2.
- HTTPS active with certificate covering staging domain.
- Migrations tested here before Production per `26_Deployment_Plan.md` §12.2.
- UAT per `24_Testing_Strategy.md` §16: Super Admin Teacher/Subscription/pricing/Platform Settings/global reports, Teacher Educational Grades/Groups/Students/Attendance three methods/Homework/Exams/Lessons/Reports/Users/Settings, Teacher Staff permission boundaries assigned permissions only BR-013, Student Dashboard/My Schedule/Homework/Exams/Lessons/Subscriptions per-Teacher partitioned/Settings registration dual methods BR-022, Parent Dashboard/Student Switcher/Homework/Attendance/Exams/Teachers/Payments Flow B read-only BR-004, Student movement history preservation BR-007.

**RC acceptance preconditions:**

- All automated tests pass: backend Feature/Unit, frontend integration, as per `24_Testing_Strategy.md` §20.1.
- No Critical/High bugs open per §17.2 bug resolution priority.
- Business rule coverage per §21.
- Authorization matrix verified.
- Teacher Workspace isolation verified across modules.
- Archive behavior verified.
- Audit Log coverage verified mandatory ten events.
- Flow A/B separation verified.
- Historical preservation verified.
- Security checklist passes `23_Security_Standards.md` §21.
- Environment checklist passes `35_Environment_Configuration.md` §22.3.
- Release documentation §15 and change log §16 complete.

**Hand-off:**

- Upon acceptance, RC branch merges to main via merge commit per `36_Git_Workflow.md` §13 and §16. Production tag `v1.0.0` created from main. Merge back to develop brings hardening fixes.

# 9. Hotfix Release Process

Hotfix addresses Critical or High bugs discovered in production main per `36_Git_Workflow.md` §7 and rollback triggers per `26_Deployment_Plan.md` §19.1.

**Examples triggering hotfix:**

- Teacher Workspace isolation breach BR-003 data leak between Teachers.
- Duplicate Student accounts created violating BR-001 global account and BR-022 dual methods.
- Audit Log entries lost or modified violating BR-006 immutable permanent.
- Archive replaced by hard deletion violating BR-005.
- Historical data lost or corrupted violating BR-007/BR-014.
- Flow A/B conflation causing Subscription vs payment status misreporting.
- Authentication or authorization broken.
- Platform unavailable extended period.

**Origin and branch:**

- Branch originates from main at production tag marking current release, naming `hotfix/teacher-workspace-isolation-leak-br003` per `36_Git_Workflow.md` §9. Minimal surgical fix only, no features, no scope expansion, no PENDING hardening.

**Dual merge requirement:**

- After acceptance, merges to both main (patch tag `v1.0.1`) and develop (so future releases include fix). Second merge conflict resolution preserves hotfix intent per Git Workflow §7 and §14.

**Quality gates expedited but complete:**

- Test reproducing defect before fix and verifying after per `24_Testing_Strategy.md`.
- Isolation tests, duplicate prevention tests, Archive tests, Audit Log tests as applicable.
- Security checklist review for isolation, file access, rate limiting, session flags.
- Environment check minimal but includes isolation and Audit Log integrity.

**Approval workflow expedited per §11 but not bypassed:** Product Owner and Architect approve, Super Admin notified for Platform scope.

**Documentation:**

- Change log entry with severity Critical/High, BR references, resolution.
- Post-release monitoring per `27_Development_Roadmap.md` §17.4: operational logs and Audit Log for anomalies.

**Solo optimization:** Hotfix branches rare and short; solo developer validates in staging-like local environment mirroring production config.

# 10. Patch Release Process

Patch releases are non-urgent bug fixes discovered in develop or staging before production or as part of scheduled maintenance after production,区别于 hotfix urgency.

**Trigger:**

- Medium/Low bugs per `24_Testing_Strategy.md` §17.1, e.g., incorrect error message, missing empty-state, filter unexpected, pagination count incorrect, canonical terminology label inconsistency.
- Also covers small hardening discovered during RC stabilization: query optimization preserving workspace scoping, cache scoping fix, validation enhancement without behavior change.

**Origin:**

- Bugfix branch originates from develop for pre-production patch, naming `bugfix/` per Git Workflow §9, or from release branch during RC lifecycle as fix commit.
- For post-production non-urgent patch, fix goes to develop first, then included in next release branch, eventually main as patch tag `v1.0.2` etc., following release flow §8 but with smaller scope.

**Flow:**

- Bugfix branch → develop via PR squash merge per Git Workflow §13.
- Develop tip tested via Testing release process §6.
- When next release branch created from develop, patch included.
- Release branch hardening includes patch, then merges to main with patch tag.

**Distinction from hotfix:**

- Patch does not originate from main production tag unless it qualifies as hotfix per severity Critical/High. Patch waits for normal release cadence; hotfix bypasses normal cadence but still follows checklist.

**Version impact:**

- PATCH increment per SemVer `27_Development_Roadmap.md` §18.2 (1.0.0 → 1.0.1, 1.0.2). PATCH never introduces new features or changes frozen business rules.

**Documentation:**

- Change log entry classified as Patch, with module affected, BR reference if any, non-breaking nature.

**Future VPS/Cloud:** Patch process identical; only verification includes new infrastructure-specific checks like Supervisor-managed queue worker.

# 11. Release Approval Workflow

Approval workflow governs who must approve and which gates must pass before any release progresses.

**Roles in approval:**

- **Product Owner:** Scope authority, owns `00_Project_Context.md` frozen authority and `01_Project_Vision.md`. Approves major/minor releases and any change touching PENDING resolution. Confirms Version 1 scope lock `27_Development_Roadmap.md` §18.3 not violated.
- **Architect / Technical Lead:** Architecture, documentation, database, backend, frontend, API, development planning per `00_Project_Context.md` §17 collaboration protocol. Maintains canonical document set AI_DOCS/. Reviews for consistency, isolation, business rule enforcement.

# 14. Rollback Procedure

Rollback procedure defines decision, execution, and verification steps when release must be reverted, per `26_Deployment_Plan.md` §19, `27_Development_Roadmap.md` §17.3, `35_Environment_Configuration.md` deployment milestones, and `36_Git_Workflow.md` §17 Git-level aspects.

**Rollback triggers (must rollback if any true):**

- Critical bug discovered post-deployment per severity `24_Testing_Strategy.md` §17.1: cross-Teacher data access BR-003, duplicate Student accounts BR-001/BR-022, Audit Log loss BR-006, permanent deletion BR-005.
- Teacher Workspace isolation violated in any module: Educational Grades, Groups, Students, Attendance, Homework, Exams, Lessons, Reports, Teacher Staff, Settings, payment-status, files.
- Historical data lost or corrupted: Student transfer history BR-007, Billing Cycle history BR-014, archived records indication lost.
- Audit Log entries lost or modified: mandatory ten events missing, immutability violated.
- Flow A and Flow B conflated: Subscription calculation reads Flow B data or payment-status reads Flow A.
- Authentication or authorization broken: Laravel Sanctum session invalid, Gates & Policies bypassed, Student self-scope bypassed, Parent linked-Student scope bypassed.
- Platform unavailable extended period: cPanel Cron Scheduler not executing, Database Queue worker not processing, MySQL 8 connectivity failure, Apache/LiteSpeed misconfiguration.
- High financial misreporting: Billable Student calculation using Attendance/login instead of enrollment duration >15 days BR-008.

**Decision authority:**

- Rollback decision requires Architect and Product Owner approval, Super Admin notification for Platform scope. For emergency per §19, expedited approval but same triggers.

**Execution phases (policy-level description):**

- **Application code rollback:** Identify previous production tag on main that passed full acceptance per §8. Restore application code from version control tag or release archive counterpart. Reinstall dependencies for previous version via deployment plan process. Re-cache configuration, routes, views, events per `35_Environment_Configuration.md` §7.3. Verify connection to database and storage, isolation still enforced. Git-level: rollback does not rewrite main history that has been published; instead new commit or hotfix branch restores previous tag content as new commit per `36_Git_Workflow.md` §17, preserving tag history immutable.

- **Database rollback:** Evaluate Laravel migration rollback capability for affected migrations without permanently deleting data. If migration adds column, rollback removes column but data strategy must preserve historical requirements per `26_Deployment_Plan.md` §12.4. If rollback not possible without data loss, restore database from most recent pre-deployment backup per pre-deployment checklist. Verify restored database preserves Teacher Workspace isolation, Archive state, Audit Log integrity, historical relationships, Flow A/B separation, enrollment time-bounded periods, Billable Student calculation. Verify database consistent with restored application code.

- **Frontend rollback:** Restore previous compiled frontend build from backup: replace public/build/ directory with previous build output per deployment plan. Frontend build fingerprinted by Vite per `35_Environment_Configuration.md`. Verify frontend loads correctly and communicates with backend via `/api/v1` prefix, React Router client-side routing works, file and QR browser coordination preserved.

- **Storage rollback:** Verify file references remain valid if storage changes made during failed deployment. Restore files from backup if necessary preserving Teacher Workspace ownership teacher-workspaces/lessons/homework/files vs student-homework, private Lesson ownership BR-018, Student Homework submission privacy, historical references retained per `20_File_Storage.md`.

**Constraints (mandatory per `26_Deployment_Plan.md` §19.3 and Git Workflow §17):**

- Rollback must not permanently delete data. Archive replaces deletion everywhere BR-005.
- Rollback must preserve Teacher Workspace isolation BR-003.
- Rollback must preserve Audit Log integrity BR-006; rollback actions themselves produce Audit Log entries where applicable (Subscription Change, Permission Change if relevant).
- Rollback must preserve Flow A/B separation.
- Rollback must not weaken authentication or authorization.
- Backup artifacts must not be committed, must be stored separate, encrypted where host supports, access restricted.

**Post-rollback verification:**

- Execute post-release checklist §13 again on rolled-back version.
- Verify no Critical/High bugs remain from previous failure.
- Communicate rollback per §17 including version reverted from/to, reason (trigger), impact scope (which Teacher Workspaces, which Student accounts, which Parent linked Students, if any), remediation timeline.

**Git tagging for rollback:**

- Tags for failed release remain in history as immutable record. New tag marks rollback state, e.g., if `v1.0.2` failed, rollback to `v1.0.1` content is tagged as `v1.0.3` noting revert of `v1.0.2` in message, or as hotfix tag. This preserves Archive philosophy and auditability.

# 16. Change Log Standards

Change log provides chronological, human-readable record of versions, aligned with `28_Coding_Standards.md` §14 commit message convention and `27_Development_Roadmap.md` versioning.

**Format principles:**

- Change log is ordered reverse chronological: newest version first.
- Each version section includes: version number `vMAJOR.MINOR.PATCH`, date, roadmap milestone (e.g., M3 Teacher Workspace complete, M11 Production Release), tag reference, and categorized lists.
- Categories mirror commit types: Added (feat), Changed, Fixed (fix), Refactored (refactor), Documentation (docs), Tests (test), Chore (chore), Performance (perf), Reverted (revert). Breaking changes include `BREAKING CHANGE:` footer reference.
- No source code, no command sequences, no pipeline definitions inside change log.

**Content rules:**

- Entries use imperative mood short description <=72 chars conceptual similar to commit convention, e.g., "add Dynamic QR Code daily generation per BR-010", "prevent duplicate Student account creation per BR-001/BR-022".
- Entries use canonical terminology: Educational Grades CRUD not Classes, Lessons not Courses, Archive not Delete, Teacher Workspace isolation not tenant isolation in product contexts, Subscription Flow A only, payment status Flow B.
- Traceability: each entry that enforces business rule references BR-xxx; each that implements decision references D-xxx.
- Flow separation explicit: Subscription calculation changes listed under Subscription (Flow A) category, payment-status changes under Payments (Flow B).
- No secrets, credentials, hostnames, IPs, or real data.

**Example conceptual entry structure (descriptive, not code):**

- Version `v1.0.0` dated, milestone M11 Version 1 Release on cPanel Shared Hosting primary target, stack Laravel 12 PHP 8.3 React 19 MySQL 8.
  - Added: Educational Grades management within Teacher Workspace per BR-003 isolation, Groups with Name/Schedule/Price/Pricing Type Monthly/Per Lesson per BR-009, Student registration dual methods self-registration and Teacher-created with duplicate prevention per BR-022 and one global account per BR-001, Student belongs to one Group per Teacher BR-002, Parent linked-Students one Parent per Student BR-020 Student Switcher read-only BR-004, Attendance three methods Dynamic QR Code daily/ID Card/manual per BR-010, Homework Text/Image/PDF only per BR-021 video rejected, Question Bank private four types Multiple Choice/True/False/Essay/Bubble Sheet per BR-011 with Bubble Sheet electronic auto-grading D-010, Lessons Teacher-owned private per BR-018, Teacher Staff creating workspace assigned permissions only per BR-013, Platform Super Admin Teachers/Subscriptions/pricing/platform settings/global reports, Billing Cycle calendar month D-006 first to last auto new cycle, Billable Student enrollment duration >15 days BR-008 D-007 attendance/login not used Monthly Subscription = Billable × Price Per Student.
  - Fixed: relevant bugfixes per patch.
  - Security: HTTPS required production D-039, session cookies HttpOnly/Secure/SameSite, rate limiting File Cache.

**Pseudocode or code snippets prohibited:** Change log must not contain implementation code, only business intent.

**Governance:**

- Change log authored as part of release branch hardening, reviewed in RC approval per §11.
- Change log remains consistent with previous documents: must not invent business rules, must reference owning documents.

**Future continuous delivery:**

- When future continuous delivery per §20 becomes approved, change log may be generated from commit messages automatically but still reviewed for canonical terminology and BR traceability.

# 19. Emergency Releases

Emergency releases handle immediate production issues requiring bypass of normal RC duration but never bypassing quality gates or checklist discipline.

**Definition:**

- Emergency release is a hotfix or patch that must reach Production faster than normal release cadence due to Critical bug, Platform unavailable extended, isolation breach, Audit Log loss, historical corruption, Flow conflation causing financial misreporting.

**Difference from standard hotfix:**

- Standard hotfix per §9 also urgent but may still undergo RC-like staging validation shortened. Emergency release accelerates timeline further, may skip prolonged UAT if UAT representatives unavailable, but must still satisfy pre-release checklist §12 critical subset and post-release checklist §13, and must still have Product Owner and Architect approval expedited.

**Triggers (same as rollback triggers per §14 and `26_Deployment_Plan.md` §19.1 plus emergency criteria):**

- Teacher Workspace isolation violated in production with evidence of cross-Teacher data exposure.
- Duplicate Student accounts created in production violating one global account.
- Audit Log entries lost or modified in production.
- Historical data lost or corrupted in production.
- Flow A/B conflated causing Subscription miscalculation (Billable Student using Attendance).
- Authentication or authorization broken causing 401/403 for all roles.
- Platform unavailable extended period: application availability monitoring indicates downtime per `26_Deployment_Plan.md` §20.2.

**Process (policy-level, no command sequences):**

- **Detection:** Monitoring per `26_Deployment_Plan.md` §20 application availability, database connectivity, queue processing status, Cron execution, disk usage, error rates, failed login attempts per `23_Security_Standards.md` §19, Audit Log integrity, plus user reports via Super Admin.
- **Containment:** Immediately contain incident by revoking access, invalidating sessions, isolating affected Teacher Workspaces if needed, per `23_Security_Standards.md` §20 incident response. Record incident as Audit Log event.
- **Branch creation:** Hotfix branch from main at current production tag per Git Workflow §7, naming `hotfix/` with defect description canonical terms.
- **Fix development:** Minimal surgical fix preserving frozen scope and PENDING discipline. Includes test reproducing defect before fix per `24_Testing_Strategy.md` bug reporting workflow §17.2: severity, role context, module, steps to reproduce, expected/actual, BR reference, environment.
- **Expedited validation:** Run full relevant test subsets locally, especially isolation regression, Archive regression, Audit Log regression, Flow separation regression, plus security checklist relevant. Staging validation abbreviated but includes isolation and Audit Log integrity verification on staging cPanel separate account.
- **Approval expedited:** Product Owner and Architect approve via emergency approval workflow §11 expedited, Super Admin notified, QA/UAT may be post-release if pre-release UAT impossible, but post-release UAT mandatory.
- **Deployment:** Production deployment per `26_Deployment_Plan.md` §11 backend §10 frontend but with expedited window communication per §17 release communication including emergency notice.
- **Tagging:** Patch version increment `v1.0.x` with tag message indicating emergency nature, trigger, and rollback reference.
- **Merge back:** Dual merge to main and develop per Git Workflow §7 and §13 to keep future releases consistent.
- **Post-release monitoring:** Per `27_Development_Roadmap.md` §17.4: monitor operational logs and Audit Log for anomalies, verify background jobs Billing Cycle, Billable Student enrollment duration only, Subscription snapshot, QR cleanup, Exam auto-grading, report preparation, Cron execution, Database Queue worker processing. Confirm no Critical/High bugs in first operational period.
- **Post-mortem:** Document incident category per `23_Security_Standards.md` §20.2 authentication compromise, authorization bypass, data exposure, tenant isolation violation, denial of service, malware upload, plus incident response procedures detection/containment/investigation/remediation/notification/post-incident review. Audit Log serves as forensic evidence per §20.4.
- **Rollaback readiness:** Even emergency release must have rollback procedure §14 reviewed and previous version backup available per pre-deployment checklist.

**Prohibitions during emergency releases:**

- No hardening of PENDING Q-005/Q-010/Q-011/Q-012/Q-013/Q-015 as part of emergency fix.
- No out-of-scope feature introduction (native mobile, payment gateways, notifications, marketplace, video homework).
- No secrets committed, no generated artifacts committed.
- No history rewrite; rollback via new commit/hotfix.

**Communication for emergency releases:**

- Release communication §17 includes emergency notice: version reverted from/to if rollback, reason trigger, impact scope Teacher Workspaces/Students/Parents affected, remediation timeline, plus generic security notice without vulnerability detail that would aid exploitation.
