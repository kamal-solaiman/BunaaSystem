# 38 — Backup & Recovery

## Document Scope

This document defines the official Backup and Recovery strategy for Version 1 of the Unified Education Platform. It describes how application data, uploaded files, configuration, and databases are protected, backed up, restored, and verified.

It is a process and governance document only. It does not define source code, shell scripts, backup command sequences, Cron command contents, CI/CD pipeline definitions, infrastructure-as-code, database tables, SQL, API implementation, or UI implementation.

`AI_DOCS/00_Project_Context.md` is the official Single Source of Truth and prevails if any conflict is found. The technology baseline is **Laravel 12** backend with **PHP 8.3**, **React 19** frontend with **TypeScript**, **Vite**, **Tailwind CSS**, **MySQL 8**, **Laravel Sanctum**, **Laravel Gates & Policies with Custom RBAC**, **File Cache**, **Database Queue**, **Database session driver**, **Laravel Public Storage**, **Laravel Scheduler with Cron Jobs**, **SMTP** baseline, **Apache or LiteSpeed**, on **cPanel Shared Hosting** primary target with **VPS / Cloud** as future target, per `03_System_Architecture.md` §4.1, `04_Project_Structure.md`, and `29_Project_Decisions.md` D-001, D-044.

Backup and deployment relationship: backup scope, storage, encryption, isolation, integrity verification, and restoration steps are introduced in `26_Deployment_Plan.md` §18-§19 and `35_Environment_Configuration.md` §24.2; monitoring in `26_Deployment_Plan.md` §20; security in `23_Security_Standards.md` §17; file storage ownership in `20_File_Storage.md`; background job failure handling in `21_Background_Jobs.md`; Git tagging immutability and version restore in `36_Git_Workflow.md` §15-§17; release rollback checklist in `37_Release_Management.md` §14. This document consolidates and standardizes those scattered requirements into one authoritative backup and recovery reference. It invents no new backup topology, no secret values, no storage hostnames.

**Authoritative sources:** `00_Project_Context.md`, `03_System_Architecture.md`, `04_Project_Structure.md`, `06_Database_Design.md`, `07_Data_Dictionary.md`, `20_File_Storage.md`, `21_Background_Jobs.md`, `23_Security_Standards.md`, `24_Testing_Strategy.md`, `26_Deployment_Plan.md`, `27_Development_Roadmap.md`, `30_Project_Glossary.md`, `31_Master_Index.md`, `35_Environment_Configuration.md`, `36_Git_Workflow.md`, `37_Release_Management.md`.

# 2. Backup Philosophy

Backup philosophy inherits Archive and Audit Log philosophy and deployment objectives `26_Deployment_Plan.md` §2:

1. **Historical data is never deleted; backups prolong that guarantee.** BR-014 requires historical data always available, reports include archived records clearly indicated. Backup extends this beyond live database lifetime.

2. **Archive replaces deletion in product; backup replaces loss in operations.** No hard delete exists anywhere per BR-005, even Super Admin has no delete permission. Backup ensures Archive state itself is not lost due to infrastructure failure.

3. **Audit Log immutability extends to backup integrity.** Audit Log entries append-only immutable permanent per BR-006 and `23_Security_Standards.md` §15 properties append-only/immutable/permanent retention/transactional guarantee/attribution. Backup must preserve these properties; restore must not edit, archive, or delete Audit Log entries even during incident response per `23_Security_Standards.md` §20.4.

4. **Tenant isolation preserved in backup and restore.** Teacher Workspace isolation BR-003 is highest-priority invariant. Backup artifact must preserve isolation meta context; restore must not mix data across Teacher Workspaces; backup handling must not make protected files public or expose storage paths/credentials per `26_Deployment_Plan.md` §18.6.

5. **Flow A / Flow B separation preserved in backup.** Teacher → Platform Subscription Flow A and Student/Parent → Teacher fees Flow B are separate architectural concerns never conflated per `00_Project_Context.md` §5.2 and D-036. Backup storage, verification, and restore must keep separation.

6. **One codebase, environment-specific configuration, never in version control history.** Same application runs in Development, Testing, Staging (Future), Production per `35_Environment_Configuration.md` §3. Secrets live only in deployment-managed environment files, `.env` never committed per `23_Security_Standards.md` §16.2 and `26_Deployment_Plan.md` §8.1. Configuration backup is encrypted and access-restricted, not committed.

7. **cPanel Compatible by design.** Version 1 primary target cPanel Shared Hosting D-044. Backup mechanism must operate within shared hosting limits: File Cache, Database Queue, Database session driver, Laravel Public Storage, Scheduler via cPanel Cron Jobs, no Docker, Redis, Kubernetes, S3, WebSockets, Microservices as mandatory.

8. **Verification before trust.** Backup without verification is not a backup. Integrity must be verified periodically through test restores that confirm Teacher Workspace isolation, Archive state, Audit Log integrity, historical relationships, Flow separation per `26_Deployment_Plan.md` §18.5 and `23_Security_Standards.md` §17.2.

9. **No silent hardening of PENDING.** Backup strategy does not resolve open questions Q-005 non-payment enforcement, Q-010 Lesson video hosting/protection private storage signed short-lived playback URLs streaming-only per-Teacher quota proposed default, Q-011 Teacher Staff permission granularity fixed capability-flag catalog saveable presets, Q-012 Super Admin content visibility aggregates/finances/metadata only, Q-013 flat price vs volume tiers, Q-015 timezone/currency Arabic-first RTL + English. Backup configuration does not harden these.

10. **Future-proof without overbuilding.** Backup choices must not prevent future migration to VPS/Cloud per `26_Deployment_Plan.md` §24-§25 and `35_Environment_Configuration.md` §23. Version 1 does not require managed database snapshots or object storage versioning, but must not preclude them.

# 3. Backup Objectives

- **Deliver reliable recoverability on cPanel Shared Hosting.** Platform must be restorable to known-good state after infrastructure failure, accidental data corruption, or Critical bug, without requiring infrastructure beyond cPanel baseline.

- **Preserve all business invariants across backup/restore boundary.** Teacher Workspace isolation, one global Student account BR-001/BR-022, one Group per Teacher BR-002, Parent read-only linked only BR-004, one Parent per Student BR-020, Archive BR-005, Audit Log BR-006, historical preservation BR-007/BR-014, Flow separation, Teaching Subject immutability BR-016, Homework formats BR-021, Attendance three methods BR-010, Question Bank private four types BR-011.

- **Protect sensitive configuration separately.** Application code version-controlled in Git per Git Workflow main/develop/feature/hotfix/release/arena model `36_Git_Workflow.md`; no backup needed beyond repository for code itself. Sensitive configuration backed up encrypted and access-restricted.

- **Enable repeatable verification.** Backup integrity verification produces consistent, auditable evidence that restored database preserves isolation, Archive, Audit Log, Flow separation.

- **Minimize data loss within shared hosting constraints.** Define RPO per §17 that balances cPanel capabilities with operational needs; daily minimum backups for MySQL database and file references per `26_Deployment_Plan.md` §18.2, more frequent where hosting supports.

- **Minimize downtime with rollback capability.** Support rollback capability if deployment introduces Critical bug, isolation violation, historical corruption, Audit Log loss, Flow conflation, auth broken, extended unavailability per `26_Deployment_Plan.md` §19.1 and `37_Release_Management.md` §14 rollback triggers.

- **Support future VPS/Cloud without redesign.** Backup decisions must remain compatible with future managed database automated backups, object storage versioning, CDN, load balancing, auto-scaling with isolation preserved.

# 5. Database Backup Strategy

Database backup strategy preserves MySQL 8 persistence layer with InnoDB engine utf8mb4 charset utf8mb4_unicode_ci collation per `26_Deployment_Plan.md` §4.3 and `35_Environment_Configuration.md` §12.1.

**Engine and charset preservation:**

- InnoDB default MySQL 8, utf8mb4, utf8mb4_unicode_ci. Backup must retain charset/collation and avoid conversion that would corrupt Arabic-first RTL content PENDING Q-015 but prepared via utf8mb4.

**User privilege separation:**

- Production database user privileges minimum: CREATE/SELECT/INSERT/UPDATE/DELETE/INDEX/ALTER/CREATE TEMPORARY TABLES/LOCK TABLES per `26_Deployment_Plan.md` §4.3; must not have DROP/ALTER DATABASE/GRANT in production per security §11.3 and `35_Environment_Configuration.md` §12.2. Backup operation uses separate privileged backup user with read and locking capabilities, not application user; backup user credentials not stored in version control, managed per backup security §18.

**Contents including governance tables:**

- Application tables as per scope §4 plus session table per Database session driver D-040 periodic cleanup expired sessions per `23_Security_Standards.md` §7.4, queue jobs table and failed jobs table per Database Queue D-042 processed jobs cleaned weekly per `35_Environment_Configuration.md` §14.4 and `21_Background_Jobs.md`, Audit Log table append-only immutable permanent retention per §21.3.

**Consistency considerations:**

- Backup must occur during low-activity window or with appropriate locking/transactional consistency to avoid capturing partial enrollment closure/opening during Student transfer BR-007 history preservation, partial Billing Cycle initialization first day D-006, Billable Student calculation enrollment duration only D-007, Subscription Snapshot Generation last day immutable D-003 proposed. Backup integrity must reflect time-bounded Enrollment periods referencing structure as of recording time.

**Isolation preservation in backup artifact:**

- Backup artifact itself must contain Teacher Workspace ownership columns (e.g., teacher_workspace identification) to allow verification that restoration preserves isolation meta context. Verification per §11 must confirm restored database preserves Teacher Workspace isolation BR-003; restore must not mix data across Teacher Workspaces per `26_Deployment_Plan.md` §18.6.

**Archive and Audit Log preservation:**

- Archive state active/archived representation must be backed up; archived records excluded from active searches/dropdowns but included in reports clearly indicated must remain available after restore per Project Context Archive Policy §11 and BR-014. Audit Log entries must not be purged, archived, compacted per Audit Log properties §10.3 append-only immutable permanent retention per `23_Security_Standards.md` §15.4 transactional guarantee same transaction as action.

**Flow separation preservation:**

- Flow A Subscriptions and Flow B payment-status separate persistence and reporting paths must be preserved in backup and verified after restore: Monthly Subscription = Billable × Price Per Student BR-008 vs Group Price Pricing Type BR-009.

**No real credentials or paths in this document:** Database host, port default 3306, database name, username, password described only as placeholder meanings per `35_Environment_Configuration.md` §10.3, never real values.

**No backup commands or shell scripts:** This document does not describe executable dump commands or script file contents; it describes policy and verification only per task prohibition.

# 9. Backup Retention Policy

Retention policy defines how long backup artifacts remain available for restore, balancing historical needs BR-014 and storage limits cPanel Shared Hosting.

**Principles from `26_Deployment_Plan.md` and `23_Security_Standards.md`:**

- Historical data is never deleted and must always remain available per BR-014 reports/history queries include archived records clearly indicated, Audit Log permanent per BR-006. Backup retention must ensure ability to restore historical point, not to permanently delete historical data.

- No hard delete exists anywhere per BR-005; archival cascades defined per entity in `06_Database_Design.md` must not archive historical records. Retention policy for backups mirrors product Archive: backups superseded but marked superseded, never silently erased without replacement.

- Application code retains full history via Git tags immutable per `36_Git_Workflow.md` §15; release branch retention after merge supports diagnosis if rollback needed.

**Retention categories (operational decision, examples as policy guidance not executable values):**

- **Daily database backups:** Retained for short operational window sufficient for immediate rollback per `26_Deployment_Plan.md` §26.3 rollback checklist previous application code version identified available, pre-deployment DB backup available, pre-deployment file storage backup available. Short retention aligns with daily minimum frequency.

- **Pre-deployment backups:** Retained for at least duration of deployment milestone validation per `27_Development_Roadmap.md` §16 DE9-DE10 and post-release monitoring per §17.4 operational logs Audit Log background job processing Cron Queue error rates.

- **Weekly file storage backups:** Retained longer than daily because Lesson videos and Homework submissions represent Teacher-owned private educational content BR-018 with historical value, preserved through Student Group movement BR-007.

- **Configuration backups encrypted:** Retained with same lifecycle as environment they protect, with encryption key separation per §18.4; old configuration backups containing rotated credentials handled per backup security access restricted.

- **Superseded backups:** Marked superseded with pointer to replacement, never deleted without replacement, mirroring documentation retiring rule `31_Master_Index.md` §13.6 and Archive policy.

- **Audit Log backup retention:** Audit Log entries stored in MySQL database not file-based logs per `26_Deployment_Plan.md` §21.3 subject to permanent retention rules per `35_Environment_Configuration.md` §19.2 backup rotation and cleanup must never delete or modify Audit Log entries per §21.3-§21.4. Backup retention must not purge Audit Log entries.

**cPanel Shared Hosting constraints:**

- Disk space limited, sufficient for application code, MySQL database, Public Storage files, operational logs per `26_Deployment_Plan.md` §4.1. Retention must balance disk watch per `35_Environment_Configuration.md` §24.2 disk watch log rotation queue-table maintenance storage growth primary levers `26_Deployment_Plan.md` §20.2 §21.3.

**Future VPS/Cloud retention evolution:**

- VPS/Cloud may allow managed database automated backups retention policies with longer windows, object storage versioning, cross-region replication, per `26_Deployment_Plan.md` §25 opportunities and `35_Environment_Configuration.md` §23.2. Retention policy must adapt to preserve isolation and Archive/Audit Log immutability.

**No real storage paths:** Retention locations described as separate from production server, not absolute paths.
