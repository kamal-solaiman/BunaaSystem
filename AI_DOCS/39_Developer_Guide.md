# 1. Document Purpose

The purpose of this developer guide is to give any new or existing developer a single, safe entry point to the Unified Education Platform. After reading this guide, a developer should be able to:

- Understand the real problem the Platform solves: fragmentation when one Student studies with several Teachers on different platforms, with different credentials, QR codes, Attendance systems, Homework sources, and Exams.
- Understand the confirmed solution: one Platform, one global Student account, one Parent account, many completely isolated Teacher Workspaces, private Teacher-owned Lesson videos, and clear separation of Flow A (Teacher → Platform Subscription) and Flow B (Student/Parent → Teacher fees).
- Know exactly which documents to read and in which order before writing any code, per `31_Master_Index.md`.
- Prepare a local development environment that mirrors the production baseline without requiring Docker, Redis, Kubernetes, S3, WebSockets, or Microservices.
- Navigate the repository structure safely and know where a file or folder belongs per `04_Project_Structure.md`.
- Follow mandatory coding standards, Git workflow, and branch strategy without inventing new conventions.
- Respect database, API, frontend, backend, security, testing, debugging, and logging guidelines owned by their respective documents.
- Contribute through a common workflow and pull request process that preserves Teacher Workspace isolation (BR-003), Archive instead of deletion (BR-005), and immutable Audit Log (BR-006).

Out of scope: This guide does not add business rules, does not define API endpoints, does not define database tables, and does not provide implementation code. All rules are traceable to BR-xxx, D-xxx, Q-xxx from `00_Project_Context.md`.

# 2. Project Overview

The Unified Education Platform is a SaaS educational platform where Teachers pay a monthly Subscription based on Billable Students. The Platform solves account and data fragmentation.

**Confirmed user roles — 5 only, per `00_Project_Context.md` §6:**

- **Super Admin:** Owns the Platform at Platform-level scope only. Manages Teachers, Subscriptions (Flow A), pricing owned by Super Admin (BR-015), platform settings, global reports within pending content-visibility boundary (Q-012). Does not operate inside Teacher Workspaces.
- **Teacher:** Operates one completely isolated Teacher Workspace, cannot access another Teacher's data under any circumstance (BR-003). Manages Educational Grades, Groups, Students, Attendance, Exams, Homework, Lessons, Reports, Users (Teacher Staff), Settings. Teaches exactly one Teaching Subject per account, selected during registration and cannot be changed after creation (BR-016).
- **Teacher Staff:** Created by the Teacher, exists only inside that Teacher Workspace. Examples: Secretary, Assistant, Accountant. Holds only permissions assigned by the Teacher (BR-013). Permission granularity PENDING (Q-011).
- **Student:** Has exactly one global account (BR-001) and may study with multiple Teachers. Belongs to only one Group per Teacher at any time (BR-002) with Enrollment as time-bounded period. Separate attendance, homework, exams, Subscription status per Teacher. Two registration methods (BR-022): self-registration Method 1 and Teacher-created Method 2 that can later be activated. Duplicate accounts not allowed.
- **Parent:** Has one account and may monitor multiple linked Students (BR-020). Read-only access everywhere, sees only linked Students (BR-004). Exactly one Parent per Student in Version 1. Student Switcher allows switching between linked Students.

**Core product surfaces per `00_Project_Context.md` §7:**

- Teacher Panel: Dashboard, Educational Grades (Teacher-created levels e.g., First Preparatory), Groups (Name, Schedule, Price, Pricing Type Monthly/Per Lesson), Students (register new, assign existing, search, move between Groups history preserved BR-007), Attendance three methods (BR-010) dynamic QR Code generated daily displayed for class scanned by Student through Web Application, ID card scanned by QR scanner, manual entry, Exams from private Question Bank question types Multiple Choice, True/False, Essay, Bubble Sheet (BR-011), Reports, Users, Settings.
- Student Panel: Dashboard, My Schedule, Homework, Exams, Lessons, Subscriptions (per-Teacher Flow B status), Settings. One login, content partitioned per Teacher, Lessons only from own Teachers.
- Parent Panel: Dashboard, Student Switcher, Homework, Attendance, Exams, Teachers, Payments (Flow B records). Read-only, only linked Students.

**Explicit non-goals (binding):** NOT an online course marketplace, Teachers do NOT sell courses, no course discovery/browsing across Teachers, no mechanism by which one Teacher's content reaches another Teacher's Students.

**Version 1 exclusions:** Native mobile application (BR-017 Web Application only), online payment gateways (BR-019 records payment status only), notifications out of scope (push/email/SMS), multiple Teaching Subjects per Teacher (BR-016 one only).

# 3. Project Goals

Goals consolidated from `01_Project_Vision.md`:

- **Unify without mixing:** One account per Student, one account per Parent, many isolated Teacher Workspaces. Student studies with several Teachers without duplicated credentials. Parent monitors several Students via Student Switcher.
- **Operational independence for Teachers:** Each Teacher Workspace feels like a dedicated platform while sharing infrastructure. Educational Grades contain Groups, Groups carry Price and Pricing Type, Students belong to only one Group per Teacher.
- **Historical integrity:** Archive replaces deletion everywhere (BR-005), historical data never deleted always available (BR-014), Student transfers preserve attendance/homework/exams/grades (BR-007), Audit Log mandatory ten events append-only immutable permanent (BR-006).
- **Financial clarity:** Two distinct flows never conflated: Flow A Teacher → Platform Subscription Monthly Subscription = Billable Students × Price Per Student (BR-008 enrollment duration only >15 days, Attendance and login NOT used, Billing Cycle starts first day every calendar month ends last day same month automatically new cycle D-006), Flow B Student/Parent → Teacher fees derived Group Price and Pricing Type (BR-009). V1 records payment status only, payments handled outside Platform.
- **Trust through isolation:** Teacher Workspace isolation is highest-priority invariant, enforced at data layer every row carries Teacher identity, every query workspace-scoped, no cross-tenant foreign keys, per-tenant constraints enforce BR-002.
- **Focused Version 1:** Web Application only, not marketplace, not payment gateway, not notifications, Text/Image/PDF Homework only (BR-021 video not supported), Lesson videos Teacher-owned private (BR-018), Question Bank Teacher-owned private.

# 9. Coding Standards

Mandatory conventions per `28_Coding_Standards.md`, mandatory for all version control.

**Coding philosophy per §1:**

- Documentation First: code follows architecture; architecture follows documentation; documentation follows confirmed decisions. No feature coded without confirmed requirement, no business rule silently assumed.
- Correctness Over Cleverness: clear implementation one reading preferred over clever shortcut.
- Backend Authority: Laravel backend sole authority for authentication, authorization, tenant isolation, business rule enforcement, Audit Log creation, persistence decisions. Frontend presents authorized data collects user input never replaces backend enforcement.
- Tenant Isolation Is Non-Negotiable: highest-priority invariant every query/API response/file access/search result/report must preserve workspace boundaries.
- Archive Never Delete: no code path may permanently delete data, Archive replaces deletion everywhere historical records remain available for reports/history queries.
- Audit Everything Important: every important action produces Audit Log entry append-only immutable permanently retained.
- Canonical Terminology: all code artifacts variable names class names method names API endpoints database concepts comments commit messages must use canonical terminology `00_Project_Context.md` §19 mandatory terms Platform Teacher Workspace Educational Grade Teaching Subject Group Student Parent Teacher Staff Super Admin Subscription Flow A Flow B Enrollment Archive Audit Log Dynamic QR Code ID Card Question Bank Bubble Sheet Student Switcher Lesson Billable Student Billing Cycle Homework. Non-canonical never appear.
- Version 1 Scope Discipline: no native mobile, payment gateways, notifications, marketplace behavior, video homework, multiple Teaching Subjects per Teacher, multiple Parent accounts per Student out of scope.

- Single Responsibility: class/function/component/module one clear responsibility Controller coordinates HTTP requests Service orchestrates business workflows Repository encapsulates query logic Model represents business entity.

- Fail Fast and Safely: invalid input unauthorized access missing resources business rule violations detected rejected early as possible, error responses enough information authorized user understanding failure without revealing private data implementation details unlinked Student information.

- No Silent Assumptions: must not silently assume PENDING Q-005 non-payment enforcement Q-010 lesson video hosting Q-011 Staff permission granularity Q-012 Super Admin visibility Q-013 pricing model Q-015 localization.
- Separation of Concerns: backend business logic, frontend presentation logic, persistence database logic, no layer owns another layer responsibility.

- Testability: dependencies injectable side effects controllable business logic isolated framework-specific concerns where practical.
- No Premature Optimization: performance optimization must not bypass authorization tenant isolation Archive rules Audit Log obligations measured bottlenecks not assumptions.
