# Physical Schema Decisions — Phase 43 / 43B

`AI_DOCS/06_Database_Design.md` and `AI_DOCS/07_Data_Dictionary.md` are
**logical only**. Both state that physical schema, SQL, migrations, and models
are out of scope. This document records how the physical schema was derived
from them, so every table, column, index, foreign key, and constraint is
traceable to a source.

**The rule applied throughout:** a column exists only because AI_DOCS explicitly
requires it, or because it is mathematically necessary to implement an AI_DOCS
requirement. Nothing was added for convenience, optimization, or future use.

That rule removed things as well as added them. Two Laravel skeleton columns —
`email_verified_at` and `remember_token` — were **deleted** because no document
requires email verification or persistent login (DD-08).

**Physical naming was not invented.** `AI_DOCS/28_Coding_Standards.md` §12
supplies the canonical table names (`teacher_workspaces`, `audit_log_entries`),
the column conventions (`id`, `{table_singular}_id`, `created_at`), and the
Archive column (`archived_at`, never a name implying deletion, §12.5).

# 2. Derived decisions

Decisions that could not be read directly from AI_DOCS. Each states why it is
required, the alternatives weighed, and why the chosen option is safest.

## DD-01 — Table and column naming

**Required because** the logical documents deliberately avoid physical naming
(06 §3: "This document avoids physical naming rules for tables and columns").

**Alternatives:** invent a convention; use Laravel's inflector everywhere;
follow 28 §12.

**Chosen:** follow `28_Coding_Standards.md` §12, which supplies an explicit
table-name table, column conventions, and canonical-terminology rules.

**Why safest:** it is not a derivation at all once §12 is applied — the names
are documented. It also keeps `teacher_workspaces` (never `tenants`) and
`archived_at` (never a deletion word), which are hard requirements.

## DD-02 — Mutual references between Teacher, Teacher Workspace, and Teaching Subject

**Required because** the dictionary declares a genuine cycle of Required
references: Teacher → Workspace and Subject (§4); Workspace → Teacher (§5);
Subject → Teacher and Workspace (§31). No insert order satisfies all three if
every column is `NOT NULL` from the start.

**Alternatives considered:**

1. Drop one reference and derive it by traversal. *Rejected:* the dictionary
   marks all of them Required; removing one contradicts the specification.
2. Merge Teacher and Teacher Workspace into one table. *Rejected:* they are
   distinct entities with distinct lifecycles and Archive states, and the
   workspace is the tenant boundary referenced by every workspace-owned record.
3. Make one direction deferrable at the database level. **Chosen.**
4. Use UUIDs generated in application code so all three rows can be built
   before insert. *Rejected:* it changes the primary-key strategy platform-wide
   to solve one ordering problem, and 28 §12 documents `id`.

**Chosen:** `teachers` holds both references `NOT NULL`; the back-references on
`teacher_workspaces` and `teaching_subjects` are added by a later migration and
are nullable **only** so a row can exist before its counterpart points at it.
The logical Required rule is enforced by the application at creation time,
inside one transaction.

**Why safest:** it preserves all three references exactly as documented,
enforces one-to-one with unique constraints in the schema, and keeps the
integer-key convention. The single cost — nullable back-references — is
narrowly scoped and documented here rather than hidden.

## DD-03 — `role_user` association table

**Required because** 07 §1 states "A User may have one or more Role contexts"
and 07 §2 states "A Role is assigned to a User in a specific context." A
many-to-many relationship cannot be represented without an association table.

**Alternatives:** a `role_id` column on `users` (cannot express *many*); a JSON
array of roles on `users` (unreferenceable, unindexable, no FK integrity).

**Chosen:** a normalized association table carrying the workspace context.

**Why safest:** this is mathematically necessary, not a convenience. It is the
only representation that supports the documented cardinality while keeping
referential integrity and the workspace scoping that Teacher Staff roles need.

## DD-04 — Status columns as constrained strings, not enums

**Required because** the dictionary marks several attributes as `Status` with a
documented default of Active, but never enumerates the complete set for
`account_status`, `workspace_status`, or `permission_status`. 33 INT-15 requires
persisted statuses to be valid states, and 33 §3.4 forbids inventing values.

**Alternatives:**

1. A database enum listing invented values. *Rejected:* that fabricates a
   product decision the documents deliberately left open.
2. A boolean `is_active`. *Rejected:* the dictionary says Status, and
   33 STU-02 already confirms a third state (Pending Activation) for Student
   accounts, which a boolean cannot express.
3. `string(32)` with the documented default, validated in the application.
   **Chosen.**

**Why safest:** it stores every documented state today, adds a state without a
migration when one is confirmed, and invents nothing. Contrast with
`role_name`, `role_scope`, `scope_context`, and `event_type`, which **are**
database enums precisely because 33 §3.3 confirms those sets as closed.

## DD-05 — `affected_entity_id` carries no foreign key

**Required because** 07 §27 says the reference is to any affected logical
entity across the Platform, and 06 §8 requires historical traceability "even
when the affected record is archived."

**Alternatives:**

1. A polymorphic FK per target table. *Rejected:* impossible — a single column
   cannot reference many tables, and one FK column per entity would add dozens
   of mostly-null columns.
2. A separate audit table per entity. *Rejected:* the dictionary defines one
   Audit Log entity; splitting it would fragment "append-only, permanent."
3. An unconstrained identifier plus the entity name. **Chosen.**

**Why safest:** an FK would actively harm the requirement. Audit retention is
permanent while business records may be archived, so a constrained reference
could block a legitimate operation or, worse, invite cascade behavior that
deletes history. The pair `(affected_entity_name, affected_entity_id)` is
indexed so one record's full history is still retrievable.

## DD-06 — Audit entries carry `created_at` but no `updated_at`

**Required because** 07 §27 defines `Occurred At` as its own attribute, and
23 §15.4 makes entries append-only and immutable.

**Alternatives:** use `occurred_at` alone; keep Laravel's timestamp pair.

**Chosen:** keep `occurred_at` (the documented business time, which a queued or
replayed write must preserve) plus `created_at` (row insertion time); omit
`updated_at`.

**Why safest:** an immutable row is never updated, so `updated_at` could only
ever mislead a reader or imply mutation is expected. Its absence is a
structural signal that matches the enforcement in the model, which throws on
update and delete.

## DD-07 — `actor_user_id` is nullable

**Required because** 07 §27 qualifies the Actor Reference with "where
available", and 23 §15.2 item 5 makes **failed** logins a mandatory audit
event. A failed login against an unknown identifier has no resolvable actor.

**Alternatives:**

1. `NOT NULL` with a sentinel "unknown user" row. *Rejected:* a fabricated user
   record that no document defines, and it would pollute the identity table.
2. A separate table for actorless events. *Rejected:* splits the Audit Log and
   breaks single-stream traceability.
3. Nullable actor. **Chosen.**

**Why safest:** it records the mandatory event honestly. Recording "no actor" is
accurate; inventing one would be false data in the one subsystem that must never
lie. 23 §3.3 additionally forbids revealing whether an account exists, so
resolving an actor from a failed attempt is not always permissible.

## DD-08 — Removing `email_verified_at` and `remember_token`

**Required because** the Laravel skeleton ships both, and no AI_DOCS document
requires email verification or a persistent "remember me" login. 07 §1 lists
neither attribute.

**Alternatives:** keep them as harmless framework defaults; keep them in case
they are needed later.

**Chosen:** remove both, along with the factory's `unverified()` state.

**Why safest:** "may be useful later" is exactly the reasoning this phase
prohibits. An unused nullable column invites a future contributor to build
behavior on an unapproved assumption. This was caught by the validation suite's
"no undocumented column" check, which is now a committed test.

## DD-09 — Text lengths

**Required because** 33 §3.4 lists "exact maximum lengths for names, titles, and
descriptions" as deliberately deferred, while 33 GEN-04 requires text to be
bounded and states the maximum is "chosen at physical design time."

**Chosen:** `string(190)` for names and identifiers; `string(255)` for
descriptions; `string(32)` for status values; `string(45)` for IP addresses.

**Why safest:** 190 is the largest length safely indexable as `utf8mb4` under a
767-byte index prefix, which matters because several of these columns are
indexed or unique. 45 is the maximum textual IPv6 length — a technical fact, not
a product number. GEN-04 explicitly authorizes this choice, and no fabricated
limit is shown to users.

## DD-10 — `restrictOnDelete` on every foreign key

**Required because** 06 §14 states cascades "must never perform permanent
deletion" and that archiving a parent "must not erase historical child records."

**Alternatives:** `cascadeOnDelete` (directly violates the rule);
`nullOnDelete` (destroys the historical link 06 §13 requires); no FK action.

**Chosen:** `restrictOnDelete` everywhere.

**Why safest:** it makes accidental hard deletion impossible at the engine
level. If application code ever attempts a real delete, the database refuses
rather than silently cascading through history. Archive is the only removal
mechanism, so restriction costs nothing in normal operation.

## DD-11 — Indexes limited to documented access patterns

**Required because** 06 §10 gives logical indexing priorities but states "full
physical indexing definitions are intentionally deferred."

**Chosen:** index only what §10 names — tenant scope, user identity lookup, role
context lookup, archive-state filtering, and audit lookup by actor, event type,
scope, and time. No speculative index was added.

**Why safest:** every index has a cost on write and storage, which matters on
shared hosting. Adding indexes for queries that do not yet exist would be the
optimization-column pattern this phase prohibits. Indexes can be added later
against measured evidence, as 28 §2.9 requires.

## DD-12 — `activation_status` has no database default

**Required because** 07 §6 lists the Default Value as "Active **or** Pending
Activation" — two values, not one. The correct initial value depends on the
registration method: a self-registered account is active immediately, while a
Teacher-created account starts pending (§6 Business Rules; BR-022).

**Alternatives considered:**

1. Default `active`. *Rejected:* a Teacher-created row inserted without an
   explicit value would silently become active, bypassing activation entirely —
   a security-relevant defect, not a cosmetic one.
2. Default `pending_activation`. *Rejected:* the mirror problem. A
   self-registered Student would be stranded pending an activation that never
   comes.
3. No default; the value is always explicit. **Chosen.**

**Why safest:** the database refuses an insert that does not state the
activation state, so neither failure mode can occur by omission. The dictionary
declines to name one default, and inventing one would harden a decision the
document deliberately left conditional.

## DD-13 — Activation Status and Account Status are separate columns

**Required because** 07 §6 lists **both** on the Student entity, and 07 §1
gives User its own distinct Account Status.

**Alternatives considered:**

1. Fold Activation Status into `users.account_status`. *Rejected:* this was
   examined closely during the Phase 43 contract review and does not hold. The
   dictionary places Activation Status on Student, not User, and gives Student
   a separate Account Status alongside it. Merging three documented attributes
   into one column would invent a design no document describes.
2. Fold Activation Status into `students.account_status`. *Rejected:* same
   objection within one entity — §6 lists them as two attributes with different
   value sets and different purposes.
3. Two columns, mirroring the dictionary. **Chosen.**

**Why safest:** it matches the specification exactly, and it keeps the two
concerns independent. An account can be archived or suspended (Account Status)
regardless of whether it was ever activated (Activation Status), and 33 AUT-13
depends on querying the activation state on its own.
