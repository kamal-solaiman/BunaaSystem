## Method: extracted, not transcribed

215 permissions × 9 fields is roughly 1,900 data points. Hand-transcription at
that scale reliably introduces errors, and a silent typo in a permission name
would become a permanent public identifier under the freeze.

The registry was therefore **generated by parsing
`AI_DOCS/09_Permission_Matrix.md` directly**: every permission name, scope,
module, role value, and note is read from the matrix tables. Verification then
re-parsed both the matrix and the generated registry independently and compared
them as sets, so the check does not trust the generator.

Derived fields — Audit impact, Archive impact, Future dependency — are computed
from documented rules (`23_Security_Standards.md` §15.2 for mandatory events,
`08_RBAC.md` §12 for Archive), not invented per row.

## What the registry records beyond the matrix

Each entry carries six derived fields, computed from documented rules:

**Roles** — collapses the four Allowed/Denied/Conditional columns into the roles
that actually have access. **119 Allowed** and **50 Conditional** grants exist
across the catalogue; the remaining columns are Denied.

**Condition** — populated only where a role is Conditional, quoting the matrix
note verbatim.

**Audit impact** — mapped to the ten mandatory events of `23 §15.2`. Writes map
to Create, Update, Archive, Restore, Permission Change, Attendance Change,
Homework Modification, Exam Modification, or Subscription Change. Reads record
none.

**Archive impact** — derived from `08 §12`: `archive` actions archive rather
than delete, `restore` actions are authorized and audited, `view_history` may
include archived records, and ordinary reads exclude them from active lists.

**Future dependency** — the honest one. Many permissions cannot be enforced yet
because their tables belong to later phases. Recording this per permission means
the implementation phase knows exactly which of the 215 are enforceable today
and which are catalogue-only.

Notable dependencies:

| Dependency | Affects |
|---|---|
| **Q-012** Super Admin content visibility | Conditional Platform entries — treat as denied |
| **Q-011** Teacher Staff granularity | All `teacher_staff` entries — no preset grant |
| `parent_student_links` (Parent phase) | The 9 Conditional Parent entries |
| Later feature tables | Attendance, Homework, Exam, Lesson, Subscription, Payment, Files, Reports entries |
| Permanently denied | Entries denied to all four roles, such as `self_assign_permission`, `login_as_teacher`, `browse_marketplace`, `process_online_payment` |

Permissions denied to every role are deliberately **kept**, not dropped. Their
presence is what makes the refusal explicit and auditable: an attempt against
`teacher_workspace.teacher_staff.self_assign_permission` is a recognized,
logged security event rather than an unknown capability.
